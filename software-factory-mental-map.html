Personal codebase workflow / September 2026

Code changes. Explicit authority.

GitHub holds intent and work state. Worktrunk isolates each code change. Codex or Claude Code work inside the approved checkout. Project checks, independent review, Plannotator, and GitHub Actions provide evidence before a human merges.

North star

Every merged change is bounded, attributable, independently checked, and explicitly approved.

The workflow ends at merged code and a clean local state. Runtime delivery is outside this map.

02 / Workflow

Five states. Two risks.

Status shows where attention is needed. Risk changes the approval and review depth without changing the delivery path.

Status field

One delivery signal

Inbox, Ready, In Progress, In Review, and Done cover the code change from unclear request to merged result. Blocked or unclear work returns to Inbox.

Risk field

Standard or Elevated

Elevated covers security, identity, secrets, personal data, destructive migrations, public compatibility, or material uncertainty. Humans may raise risk; lowering it requires an explicit decision.

Planning depth

Scale the ceremony, keep the controls.

Ask one routing question: can one person implement and validate the approved change in one session, with no unresolved product, domain, or architecture decision?

Yes / small and clear

Use the compact Standard path

Example: change the primary button from blue to an approved purple token. Record the exact component, token or value, interactive states, affected views, and contrast expectation in one GitHub Issue.

GitHub Issue→ Worktrunk→ implement→ project checks + visual QA→ code-review→ PR + Actions→ plannotator-review→ merge + cleanup
Skip: grill-me, to-spec, and to-tickets. Add focused tests only when the change exposes a meaningful behavior seam.
No / unclear or multi-session

Resolve decisions before delivery

Use planning skills only for the complexity that exists. A PRD may be an input for product-heavy work, but the factory does not require one.

grill-me or grill-with-docs→ to-spec→ Plannotator annotate→ to-tickets→ one compact delivery path per ticket
Working specification: use to-spec when accepted decisions must survive across sessions. Use to-tickets only when the approved outcome needs multiple implementation sessions.
03 / Code path

From request to clean main

Open a phase for its owner, required evidence, and stopping condition. These are workflow instructions, not behavior embedded in reusable skills.

01Clarify Inbox
Intent

Define the code change

State what should change without authorizing implementation.

Owner: human
Describe observable behavior

Capture the current behavior, expected behavior, affected interface, and smallest useful validation seam.

Bound the work

Name exclusions, blockers, uncertainty, and one reviewable outcome. Split cross-repository work into linked tickets.

Assign risk

Choose Standard or Elevated. Ambiguity defaults to Elevated until resolved.

02Prepare Ready
Isolation

Create a clean starting point

Ready means another session can begin without inventing a product or workflow decision.

Owner: operator
Verify readiness

Confirm the open ticket, approved intent, Risk, validation seam, resolved blockers, and exact base commit.

Create the worktree

Run wt switch --create <branch> --no-cd --no-hooks from the intended repository.

Run explicit setup

Inspect repository instructions, then run the project-owned setup command visibly. Move to In Progress only after setup succeeds.

03Implement In Progress
Construction

Change the approved checkout

Implementation follows repository instructions and stays inside the accepted outcome.

Owner: writable agent
Establish the baseline

Reproduce a bug through the closest user seam or demonstrate current behavior before adding new behavior.

Work in vertical slices

Add the fewest crucial behavior tests, implement the smallest robust change, and keep cleanup behavior-preserving.

Validate completely

Run project-native formatting, linting, types, focused tests, build, end-to-end checks, and the complete suite when available.

Commit by risk

Standard work may commit under approved policy. Elevated work stops for human approval of the exact candidate and message.

04Review In Progress
Independent assurance

Review without editing

The reviewer receives an explicit boundary rather than inferring workflow state from a reusable skill.

Owner: read-only reviewer
Prove the boundary

Record the original fixed point, reviewed head, comparison reference, and complete changed-file set.

Inspect sequentially

Review correctness, security, accepted intent, maintainability, and validation evidence.

Handle findings

Return a precise rework packet. Scope ambiguity returns to Inbox; accepted corrections return to Ready.

Apply elevated review

Use a different model, tool, or specialist. A missing independent reviewer requires a recorded human exception.

05Integrate In Review
Publication + merge

Merge the reviewed bytes

The pull request must preserve the reviewed head and expose all required evidence.

Owner: human + GitHub
Publish the exact head

Standard work may push and open the pull request under policy. Elevated work requires publication approval.

Require exact-head checks

Wait for required GitHub Actions and invalidate the review if the head changes.

Review visually

Use Plannotator on the CI-passing head and verify its base, head, and file set before accepting feedback or approval.

Approve merge

Merge only the reviewed candidate. Rulesets block direct default-branch changes, failed checks, force pushes, and deletion.

06Maintain Done
Closure

Verify, synchronize, clean

Completion leaves the default branch correct and local state understandable.

Owner: human operator
Verify completion

Confirm the pull request merged, the issue closed, the Project item reached Done, and required checks passed.

Synchronize main

Require a clean primary checkout, fetch, fast-forward only, and verify local and remote default-branch object IDs match.

Recheck the merged result

Run the crucial project-native verification on main and preserve evidence of the result.

Approve cleanup

Inspect branch and worktree identity, cleanliness, and unpushed state before any removal.

04 / Reusable skills

Tools, not a control plane

Skills provide portable behavior. They accept explicit context and remain independent of this Project board, its statuses, Worktrunk, and its approval sequence.

Communication

Produces concise, direct communication without owning workflow state.

Planning

grill-me

Challenges an idea until its actors, outcomes, constraints, and exclusions are clear.

Planning

grill-with-docs

Loads relevant project vocabulary before applying the grilling workflow.

Planning core

grilling

Provides the question-driven design-tree behavior used by planning entries.

Language

domain-modeling

Sharpens project terminology and records durable decisions only when justified.

Specification

to-spec

Turns approved multi-session intent into a disposable working specification. Small one-session changes skip it.

Packaging

to-tickets

Drafts bounded tickets and dependency information without changing Project state.

Construction

implement

Changes and validates an approved task in the current checkout supplied by the caller.

Construction

tdd

Guides focused test-first work at explicitly supplied observable seams.

Assurance

code-review

Reviews a supplied diff boundary for correctness, security, intent, and maintainability.

Plan review

Plannotator annotate

Reviews a materialized working specification before ticket breakdown. It is unnecessary when one approved issue is sufficient.

Code review

plannotator-review

Opens the exact CI-passing code diff for final human inspection. It does not review plans or specifications.

06 / Human gates

Approval follows consequence

Routine Standard actions may proceed within approved scope. Consequential, elevated, exceptional, and destructive actions stop for the human.

Gate 1Approve intent, Risk, validation seam, scope, and any durable decision.
Gate 2For Elevated work, approve the exact candidate and later its publication.
Gate 3Approve the exact CI-passing diff in Plannotator, then approve merge.
Gate 4Approve exceptions and destructive branch or worktree cleanup.
Direct operator seams

Commands stay visible

gh issue / project / prRead and update GitHub only within the approved change.
wt switch --create ...Create the approved exact-base worktree with hooks disabled.
project setup + checksRun repository-owned setup, formatting, linting, types, tests, build, and end-to-end commands.
git status / diff / merge-baseInspect cleanliness, changed bytes, ancestry, and review boundaries.
gh pr checks / mergeVerify the exact head and merge only the approved candidate.
Parallel work

Only after explicit approval

Parallel execution begins only for a fixed set of independent tickets. Each retains its own branch, worktree, owner, validation, review, and merge decision.

  • Record one exact starting commit for the approved wave.
  • Exclude overlapping interfaces, schemas, migrations, generated files, and shared release state.
  • Stop on new coupling, conflicts, ambiguity, or failed checks.
  • Merge sequentially unless another method is explicitly approved.
V1 boundaries

Keep the factory about code.

01The workflow ends after merge verification, main synchronization, and approved local cleanup.
02Reusable skills do not own Project statuses, worktree creation, approval order, or orchestration.
03No factory daemon, scheduler, database, wrapper CLI, automatic merger, or coordinating skill.
04Untrusted issue, pull-request, skill, and review content never grants permission or changes scope.
05Uncertain state is inspected, never forced. Dirty worktrees and divergent histories remain intact until understood.
06V1 supports one expert operator on macOS, local agents, and GitHub.com.
